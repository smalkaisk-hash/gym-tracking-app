# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FitPulse — a personal gym tracking app (React + TypeScript + Vite + Tailwind). Per the README, it's a for-fun personal project, not a product. It has a Supabase (Postgres) backend with email + password auth — open signup, forgot-password reset, and change-password in Settings (which requires the current password — see below) — and every table is RLS-scoped to `auth.uid()`. There is still no client-side router: the auth screens (`LoginScreen`, `ResetPasswordScreen`, `OnboardingScreen`, config/loader) are pre-render gates in `GymTrackerApp`, and in-app navigation is the `currentScreen` string. The server is the source of truth; localStorage is an offline read cache and the one-time migration source.

One-time Supabase dashboard setup (auth redirect URLs, email-confirmation choice, email-template copy) is documented in [SUPABASE-SETUP.md](SUPABASE-SETUP.md). The email templates are edited directly in the dashboard — nothing template-related is wired into the build.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # tsc && vite build  — tsc is the only typecheck; there is no separate typecheck script
npm run preview   # serve the production build from dist/
npm run legal     # publish legal/*.md → public/*.html (runs first in `npm run build`, so the pages can't go stale)
npm run legal:check  # verify public/ matches legal/ without writing — for CI
npm run legal:release # the launch gate: fails while any published document still has placeholders
npm run backup    # logical JSON backup of the three tables (needs SUPABASE_URL + service_role key) — see BACKUP-RESTORE.md
npm run restore   # restore a backup (defaults to a scratch target; --force-prod to overwrite prod)
npm run test:e2e  # Playwright screenshot baselines for the auth screens (needs `npx playwright install chromium` once)
```

There is no test framework, linter, or formatter installed, but there are five plain-Node assertion suites (no framework — just `node <file>`). `npm run build` plus all five is the full check; run them after non-trivial edits. There's also a Playwright screenshot suite (`npm run test:e2e`, baselines in `tests/e2e/*-snapshots/`) that guards the auth screens against silent visual regressions — it's not part of the five-suite gate but re-baseline it intentionally (`-- --update-snapshots`) if you change those screens.

```bash
node tests/unit-logic.test.mjs        # value assertions for the pure helpers (num/volume/units/duration/dates/goal)
node tests/sync-merge.test.mjs        # offline sync-reconcile (mergeUnsynced)
node tests/exercise-identity.test.mjs # slug/id collisions, starter templates, muscle overrides
node tests/legal-pages.test.mjs       # public/*.html exists, is current, and leaks nothing internal
node tests/qa/fuzz.test.mjs           # ~113 assertions over the REAL src/ bytes
```

`tests/legal-pages.test.mjs` is the counterpart to the `legal surface` guards inside `fuzz.test.mjs`: the fuzz guards assert the app's *source* wires consent, the age floor, the destructive-action names and the policy links correctly, this suite asserts the *documents those links point at* were actually built, match `legal/`, render without leftover markdown, contain no `internal:` region, **no escaped HTML comment and no drafting aside**, keep their draft marker and their placeholders in agreement, and that `legal:release` answers honestly. Neither the type system nor the bundler knows a policy link is dead — the app renders perfectly with a 404 behind it. The two suites overlap by design and duplicate no assertion: one reads `src/`, the other reads `public/`.

`tests/unit-logic.test.mjs` is the "given X, expect exactly Y" pass — it loads the real bytes through the same `load-app.mjs` harness as `fuzz.test.mjs` and asserts what the conversion/formatting/date helpers *compute*, where fuzz only asserts they stay total and in-range. A refactor that keeps a function total but changes its result is caught here, not there.

`tests/qa/load-app.mjs` is the interesting one: it reads `src/gym-tracker-app.tsx`, strips its imports, stubs them, appends an export of every top-level binding and compiles it with the project's own TypeScript — so `fuzz.test.mjs` exercises the shipping code rather than a copy of it. **A failure there is a bug in `src/`, not a broken test.** Nested helpers (defined inside `GymTrackerApp`) are sliced out by name with `extractFn`, which brace-matches — so a nested helper written as an expression body (`const f = x => x + 1;`) cannot be extracted. Prefer a block body, or lift the helper to module scope (as `clampGoal` now is).

Its last block, `guards — fixes that live outside the pure surface`, asserts against the raw source text rather than by calling anything: those fixes live in React/Supabase paths the harness can't invoke, and leaving them uncovered is what once let a half-finished sweep pass green. They catch a silent revert, not a logic error — and each one was checked to actually fail when its guard is removed.

`mergeUnsynced` still lives inline in the one big component AND is mirrored verbatim in `tests/sync-merge.test.mjs` — keep the two in step. `tests/exercise-identity.test.mjs` reads every quoted string between `const STARTER_TEMPLATES` and `const starterExercises` as a template entry, so **nothing quoted may sit between those two declarations**.

**Database schema** is versioned in `supabase/migrations/` (see its README); `schema.sql` at the root is the flattened canonical state. The dev MCP is read-only, so migrations are applied by hand in the Supabase SQL editor — `0001` (weigh-in FK) is **applied to production (2026-07-18)**: `body_weight_log.workout_id` now exists with an `ON DELETE CASCADE` FK to `workouts`. The app feature-detects the column on hydrate (`bwHasWorkoutId`) and links finish-time weigh-ins via that FK; the date-string pairing remains as the fallback for legacy/standalone rows. `0002` adds the `delete_account()` `SECURITY DEFINER` function behind Settings → Delete account (`supabase.rpc('delete_account')`); the migrations README lists it as **verify-applied** — if that button errors with "function does not exist", the file hasn't been run. Keep that table in `supabase/migrations/README.md` current: it is the only record of what is live on prod.

## Architecture

**The entire app is one file: [src/gym-tracker-app.tsx](src/gym-tracker-app.tsx).** [src/main.tsx](src/main.tsx) mounts it and imports the self-hosted font weights. Adding a feature means editing the one file, not creating new ones — match that convention unless the user asks to split things up. The exception is backend-facing *infra*, which lives in its own small module: [src/supabase.ts](src/supabase.ts) (the client + row mappers) and [src/monitoring.ts](src/monitoring.ts) (error reporting). Both are env-gated and both are auto-stubbed by the QA harness, so importing from them in the app file is safe for the Node suites.

**Error reporting is env-gated and off by default.** [src/monitoring.ts](src/monitoring.ts) exposes `initMonitoring()` (called once in `main.tsx`) and `reportError(err, ctx)`. Both are total no-ops until `VITE_SENTRY_DSN` is set — with no DSN the Sentry SDK is never loaded (it's a dynamic `import()`, so Vite dead-code-eliminates it at build when the DSN constant is empty, and code-splits it into its own chunk when it isn't). The root `ErrorBoundary` and the four otherwise-silent failure sites (migrate/hydrate/settings-upsert/import-rollback) call `reportError` *alongside* their existing `console.error` — don't remove the `console.error`s, several are asserted by the fuzz guards. To activate reporting: paste a DSN into `.env.local` and rebuild.

In file order: constants (catalogue → identity/muscle maps → storage keys → `Prefs`/`DEFAULT_PREFS`/`WIDGET_LABELS` → style strings) → the weekly-goal tile family (`LiquidWave`, `MosaicFill`, `RadialGlow`, `ProgressRing`, `PlatePips`, `LiquidNumber`, then `WeekGoalTile` which picks between them) → `SPLITS`/`TYPE_CONFIG`/`CHART`/`sanitizePrefs` → `useTheme` → `Toggle` → `SetRow` → `ExerciseCard` → `ExercisePicker` → `WorkoutScreen` → `HistoryScreen` → `MuscleGroupDonut` → `BodyWeightTrend` → `ProgressScreen` → `Segmented` → `SettingsScreen` → the auth shell (`AuthShell`, `FullScreenLoader`, `ConfigError`, `PasswordField`, `AuthHeader`) → `LoginScreen` → `ResetPasswordScreen` → `OnboardingScreen` → `GymTrackerApp` → `ErrorBoundary` → `GymTrackerAppWithBoundary`.

**`GymTrackerAppWithBoundary` is the default export**, not `GymTrackerApp` — it's a two-line wrapper at the very bottom that puts `GymTrackerApp` inside `ErrorBoundary`. `main.tsx` mounts the wrapper.

**Routing is a string, not a router.** `GymTrackerApp` holds `currentScreen` state with six values: `home`, `enterBodyWeight`, `workout`, `history`, `progress`, `settings`. Each screen is a `{currentScreen === 'x' && ...}` block in the return. `home` and `enterBodyWeight` are written inline; `workout`, `history`, `progress`, and `settings` delegate to their screen components. `settings` is opened from the header gear (`openSettings`), not the tab bar — it stashes the screen it came from in `settingsFrom` so `closeSettings` returns there. The bottom tab bar renders only outside the `workout` and `enterBodyWeight` screens (the `inSession` guard), so an in-progress workout can't be navigated away from by accident; it still shows on `settings`.

**Pre-render gates run before `currentScreen`.** In order: config-missing → `!authReady` loader → `recovery` (`ResetPasswordScreen`) → `!session` (`LoginScreen`) → onboarding → the app. Onboarding is two gates: `!hydrated && !prefs.name` shows a neutral `FullScreenLoader` during hydrate (not the onboarding card — that would greet a returning user with no cached name, e.g. after sign-out or on a fresh device, with "Welcome / set up your profile") so the dashboard doesn't flash, then `needsOnboarding` renders the interactive `OnboardingScreen`. `needsOnboarding` is set by the hydrate effect when there's no server settings row (`isFirstLogin`, captured before migration reassigns it); it collects name (required — the sentinel), units, and optional gender via one `updatePrefs` and drops the gate. **The settings write-back is gated on `!needsOnboarding`** so no row is written while onboarding is pending — its absence is exactly what `isFirstLogin` reads, so writing early would make a reload mid-onboarding skip the gate forever. Sign-out clears both `hydrated` and `needsOnboarding`. The `!prefs.name` guard keeps a returning user (cached name) on their instant cache-painted dashboard.

**Untrusted keys never index a plain object.** `TYPE_CONFIG`, `EXERCISES`, `BASES`, `ACCENTS`, `SEMANTICS`, `STARTER_TEMPLATES`, `SPLIT_BY_ID`, `MUSCLE_BY_*` and friends are object literals used as dictionaries, and their keys come from user data (an imported workout's `type`, a stored `prefs.base`, a typed exercise name). A plain `MAP[key]` walks the prototype chain, so a key of `__proto__`/`constructor`/`toString` returns a truthy `Object.prototype` member — which defeats every `?? fallback` and `? :` whitelist guarding these reads and hands a *function* to code expecting a string. **Read them with `pick(map, key)`** (own properties only) and **build user-keyed maps with `bareMap()`** (null prototype, so `map[userKey] = v` can't re-point a prototype). There is an `ErrorBoundary` around the app as the last line of defence, with a "clear this device's cache" recovery — because the crashes that matter are fed by persisted state, so a plain reload reproduces them forever.

**All state lives in `GymTrackerApp` and flows down as props.** No context, no reducer, no state library. Child components take `({ ... }: any)` — prop types are deliberately untyped throughout, and `strict` is off in tsconfig. Don't add types piecemeal to one component and leave the rest; either the user wants a typing pass or they don't.

**Persistence is Supabase (source of truth) with localStorage as an offline read cache.** Three Postgres tables — `workouts`, `body_weight_log`, `settings` (schema in [schema.sql](schema.sql)) — each RLS-scoped to `auth.uid()`. State keeps the app's original camelCase shapes; rows are snake_case, mapped at the boundary in [src/supabase.ts](src/supabase.ts). Writes are optimistic: mutate state → a write-back `useEffect` persists to localStorage → the same handler awaits the Supabase call.

localStorage holds these keys (each of the first four has its own write-back `useEffect`):

| Constant | Key | Holds |
| --- | --- | --- |
| `STORAGE_KEY` | `gym-workouts` | the workouts array |
| `BW_LOG_KEY` | `gym-bw-log` | body weight log |
| `GOAL_KEY` | `gym-weekly-goal` | weekly workout goal (int) |
| `PREFS_KEY` | `gym-prefs` | user prefs blob |
| `ACTIVE_KEY` | `gym-active-session` | in-progress workout, so a refresh can't lose it |
| `CACHE_OWNER_KEY` | `gym-cache-owner` | which user id the cached rows belong to (see below) |
| `THEME_KEY` | `gym-theme` | `light` / `dark`, only once the user picks a side |
| (direct) | `gym-theme-vars` | resolved palette for both themes, stamped by [index.html](index.html) before first paint |

On mount: a load effect paints the cache; then, once a Supabase session appears, a **hydrate** effect fetches server rows and merges them into state. First login on an account that has real local data runs a one-time localStorage → Supabase migration.

Three rules keep this from eating data:

- **Each cache key is read in its own `try`** (`readCache`). They used to share one, so a single unparsable value threw past the reads of prefs, the weigh-in log *and* the in-progress session.
- **Every write-back is gated on `signedIn`** (a stable `!!session` boolean — depending on the session *object* would re-serialise the whole workouts array on every token refresh). That stops them firing on mount with the empty initial state (previously safe only by effect ordering, and not safe at all if the load effect threw), and stops them re-writing defaults over keys that sign-out just cleared. A failed write sets `cacheWriteFailed`, which shows a banner — the offline banner promises rows are "saved on this device", and that is a lie if `setItem` threw.
- **The hydrate effect keys on `session?.user?.id`, not `session`.** supabase-js re-emits an auth event with a fresh session object on every tab focus and token refresh, so keying on the object re-ran a full three-table hydrate each time the app came to the foreground — reverting settings edits made in the previous second and re-raising a just-completed onboarding.

**A session can end without the user asking** — expired/revoked refresh token, account deleted elsewhere, sign-out in another tab — and those moments usually coincide with being offline, when the cache holds the ONLY copy of `_sync: 'error'` rows. So an involuntary loss clears neither the cache nor the in-progress workout; it only drops `hydrated`/`needsOnboarding`, and the `!session` gate hides everything anyway. The cross-user leak is closed instead by **`CACHE_OWNER_KEY`**: hydrate compares the cached owner against the signed-in user and wipes only on a genuine account change. `clearLocalCache()` is reserved for the paths where leaving *is* the intent — sign-out, clear-all-data, account deletion (and sign-out skips it if the network call threw, or the app would look signed-in over a destroyed cache).

Because hydrate no longer re-runs on tab focus, it also no longer self-heals — so **`reHydrate()`** exists: fired by the `online` event and by the banner's Retry, and `hydrateFailed` keeps the settings write-back out until a fetch has actually succeeded (otherwise a first-ever hydrate that failed offline writes a `DEFAULT_PREFS` row and suppresses onboarding forever).

**Prefs is a forward-compatible blob, sanitised on every read.** `DEFAULT_PREFS` is the schema, and **all three untrusted sources — the `gym-prefs` cache, the `settings.prefs` column, and an imported backup — go through `sanitizePrefs`**. It still merges over `DEFAULT_PREFS` (so an unknown *field* survives a round-trip and adding a field never breaks older data), but every field the app actually reads is pinned to a known-good value. This is not optional politeness: `prefs.base`/`accent`/`semantics` index palette tables, and an unknown id used to make the theme resolver throw — blanking the app on **every** device, because the bad blob syncs through the server. Add a field to `Prefs`, add its clause to `sanitizePrefs`. Profile fields `name` and `gender` (both `''` = not set) live here alongside `units` etc. — `name` doubles as the onboarding sentinel (empty = un-onboarded) and drives the home-screen `Hi, {name}` greeting. Write through `updatePrefs(patch)`, which merges and triggers the localStorage + debounced Supabase write-backs.

**Widgets are hidden per screen, not per kind.** `prefs.hidden` is a list of widget keys, and the keys are `screen.kind` (`dash.stats`, `dash.muscle`, `dash.bodyweight`, `dash.log`, `prog.muscle`, `prog.bodyweight`, `prog.exercise`) — the dotted prefix is the point: the same widget can be hidden on the dashboard and left visible on Progress. **`WIDGET_LABELS` is the registry**: it maps each key to its Settings-checkbox label, and Settings renders one toggle per entry, so a widget wrapped in a `hidden.includes(...)` guard with no `WIDGET_LABELS` entry can be hidden by a synced blob and never turned back on. Add both together. `toggleHidden(key)` is the only writer. Start-a-session and the Progress filter card are deliberately not hideable — a user can't hide their way out of being able to start a workout.

**Change-password requires the current password.** The Supabase project has "Require current password when changing password" enabled, so `changePassword(currentPassword, newPassword)` passes `current_password` to `updateUser` (cast to `any` — not in supabase-js's typed attributes). Omitting it 400s with `current_password_required`; `authErrorText` maps that (and the "must differ" rule) to friendly copy. The Settings form collects current + new + confirm.

**The legal documents are source, not decoration.** `legal/` holds the markdown: `TERMS.md`, `PRIVACY.md`, `CONSUMER-HEALTH-DATA-PRIVACY.md` and `DELETE-ACCOUNT.md` are published; `TERMS-RATIONALE.md` and `PRIVACY-POLICY-GUIDE.md` are internal reasoning and must never be. `scripts/build-legal.mjs` renders the first four into `public/*.html` with a deliberately **strict** parser that throws on anything it doesn't recognise — a page that silently drops a clause is worse than a build error — and a coverage guard that fails if a `.md` in `legal/` is in neither list. `npm run legal` runs first in `npm run build`, so `public/` can't drift from `legal/`. Conventions the parser enforces: links must be `https?:`/`mailto:`/`/`/`#` (a bare `OTHER.md` path is a build error — link to `/other.html`), headings get **no `id`s** so in-document `#anchor` links are dead and section numbers should be plain text, and **anything addressed to whoever edits the file goes inside `<!-- internal:start -->…<!-- internal:end -->`**. Two things are stripped or rejected because both once shipped inside the published Terms: *every* HTML comment is removed (the strip used to be per-line, so a comment that wrapped onto a second line fell through to the paragraph renderer and printed, escaped `-->` and all — an unterminated comment is now a build error), and a drafting aside written as `*[If you are established in …]*` is ordinary markdown, so the generator refuses it outright and tells you to wrap it.

**The draft marker and the placeholders are enforced against each other.** `<!-- legal:draft -->` stamps a visible "not yet in force" banner, and `build-legal.mjs` fails the build if a document has placeholders without the marker *or* the marker without placeholders. The first would publish `{{FILL: your project's region}}` where the recipient disclosure belongs with nothing warning the reader; the second tells every reader that a document they are asked to **accept at sign-up** is not in force — which either forms no contract at all (losing § 9's assumption of risk and § 14's cap) or is ambiguous, and § 20.6 construes ambiguity in the user's favour. `npm run legal:release` is the launch gate: it lists every unresolved fact **grouped across documents**, flagging the ones that appear in more than one so a half-resolved fact (two published policies naming different processors) is visible rather than silent. Keep one placeholder wording per fact for that grouping to work. Static files rather than app screens is deliberate: Google Play requires a non-PDF, non-geofenced, publicly reachable URL, CCPA §7011 requires the policy be printable, MHMDA requires the consumer-health-data notice to be its own separately-linked document, and Play's deletion route must work with the app uninstalled.

**A published document may not describe behaviour the code does not have.** Two shipped that did, and both are worth remembering as a class: the deletion page told users a second device's cache would clear itself on next open (the `onAuthStateChange` `!s` branch deliberately preserves it — that path also covers an expired token offline, where the cache holds the only copy of `_sync: 'error'` rows), and the privacy policy listed **Clear all data** as the way to delete the *device* copy when `clearAllData` also deletes every server row. The control is now named **Delete all my data**, the device-only action the policy points at is **Sign out** (which does clear the cache), and `clearAllData` returns `Promise<string | null>` like the other destructive handlers — Settings awaits it and shows the error, because it used to swallow a failed delete into `console.error`, clear the cache anyway and close the confirm, so an offline wipe emptied the screen while every row survived on the server. `tests/qa/fuzz.test.mjs` guards the name, the awaited call and the `reportError`.

**Sign-up carries two separate tick-boxes, and merging them is a compliance bug.** `LoginScreen` gates `Create account` on both (`unagreed`): `accepted` is acceptance of the Terms, which `legal/TERMS.md` §3.1 *defines* as this tick plus the button, and `consent` is explicit consent to health-data processing (GDPR Art. 9(2)(a)). They are distinct controls because MHMDA §19.373.010 voids consent obtained through "a consumer's agreement to general terms of use" and Art. 9 consent must be specific to the sensitive data — one combined box would invalidate the health-data half. Neither is ever pre-ticked. Both, plus the age confirmation, are recorded as Supabase **user metadata** in the same `signUp` call (`health_data_consent_at`/`_version`, `terms_accepted_at`, `terms_version`, `age_confirmed_at`) — not in `settings.prefs`, because that row is written only after onboarding completes and would lose the record if onboarding were abandoned. `SettingsScreen` displays both records back (TERMS.md §3.2 promises the user can obtain them). `MIN_AGE` is **18 because TERMS.md §4.1 says 18** — the Terms are the binding document, so don't lower it in one place only. `POLICY_VERSION`/`TERMS_VERSION` are stamped into the record so a later revision is distinguishable from what was actually agreed; bump them when a change would require re-consent. Caveat: user metadata is user-writable, so it is a record, not tamper-proof evidence — an insert-only `consents` table with RLS would be, and that's a hand-applied migration.

**Auth-access convention: gate vs in-app.** There's one rule for how a screen reaches Supabase auth, split by where it sits relative to the app mount. **Pre-render gates** (`LoginScreen`, `ResetPasswordScreen`) render *before* `GymTrackerApp`, so they have no container handlers to receive — they call `supabase.auth.*` directly and map errors with the shared `authErrorText`. **In-app screens** are the reverse: `SettingsScreen` never imports `supabase`; its auth actions (`changePassword`, `deleteAccount`, `signOut`) are injected as props and it stays presentational. When you add an auth-touching screen, follow the side it's on — a gate accesses directly, an in-app screen gets an injected handler — rather than mixing the two.

**Offline sync safety (roadmap Phase 0, implemented).** Rows carry a client-only `_sync` marker — `'pending'` (write in flight), `'error'` (saved on this device only), absent (server-confirmed). It's never sent to Postgres (the mappers in [src/supabase.ts](src/supabase.ts) pick only real columns) and it survives the localStorage cache across a reload — so if you add a field to the bodyWeightLog cache mapper (`withId` in the load effect), carry `_sync` through or a failed weigh-in loses its mark. **Hydrate merges, it does not replace:** it prefers a local unsynced edit over the stale server row (same id) and re-appends an unsynced insert whose id never reached the server; only the migration path plain-replaces. It also takes **`knownIds`** — the row ids that existed when the fetch was *issued*, snapshotted from `workoutsRef`/`bwRef`. That is what lets "absent from the server" mean "deleted remotely" rather than "written after the snapshot was taken": a row saved while the fetch was in flight (finishing a session during a token-refresh hydrate) is legitimately missing from it and must survive. The guard cuts both ways — a row that *was* in `knownIds` and is gone locally stays deleted rather than being resurrected. Failures surface as a header banner (count of device-only changes), a per-row "Not synced" chip in History, and a transient toast for self-healing failures. There is still no automatic retry/outbox — a failed write uploads on the next successful write/hydrate, not on its own; a real outbox is Phase 2.

**Import is the most dangerous path in the app** — it replaces the account. `importData` checks `app`/`version`, sanitises every row, and **refuses a file that would replace everything with nothing** (`{"workouts":[]}` used to pass the guard, delete every row and report success). Order matters: inserts and the settings upsert happen while everything is still reversible, and only then are the old rows deleted — in chunks, with **every delete's `error` checked**, rolling the import back if one fails. A discarded delete error left old and new rows side by side and still said "imported".

**Data shapes** (implicit — there are no interfaces):

```
workout       { id: uuid, type, bodyWeight, exercises[], date: ISO string, notes, duration? }
exercise      { name, exerciseId, sets[], notes }   // exerciseId (slug) is the identity; name is display
set           { reps: int, weight: float | null }   // null = bodyweight, never 0
bodyWeightLog [{ id: uuid, date: ISO string, weight }]
```

`exerciseId` is a stable slug stamped at write time (`idForName`); rows logged before it existed have only `name`, and reads derive the same id via `exerciseIdOf` (`ex.exerciseId ?? idForName(ex.name)`), so legacy and new rows unify without a backfill.

`duration` (seconds) is present only when the session timer was on. A weigh-in links to its session two ways: the durable one is the `body_weight_log.workout_id` FK (migration `0001`), which the app now writes on finish-time weigh-ins when the column is live (feature-detected via `bwHasWorkoutId`); the fallback, used before `0001` is applied and for legacy rows, is exact `date` string equality (`body_weight_log.date === workouts.date`). The client's own pairing lookup (`pairedWeighIn`, used by `updateWorkout`/`deleteWorkout`) still matches by `date` — stable and correct in both worlds since a workout's date is immutable. `deleteWorkout` removes the paired weigh-in itself (local + server) so it isn't orphaned; once `0001` is live the `ON DELETE CASCADE` also enforces this server-side for linked rows. Bulk paths (import/migrate) insert weigh-ins unlinked — the date fallback covers them, and `bwToRow` omits `workout_id` unless a `workoutId` is supplied, so no insert references the column before it exists.

**A set's `weight` is nullable.** Exercises in `BODYWEIGHT_OPTIONAL` (currently the `CORE` group) can be logged with reps alone, storing `weight: null` — bodyweight, which is distinct from a real 0. Anything reading `weight` must handle it: `?? ''` to keep an input controlled, and `!= null` before treating it as a number. For arithmetic use the `num()` helper (`volumeOf` does), which also absorbs a NaN/Infinity that would otherwise turn every volume readout on the page into `NaN`.

**A rejected weight is held, not converted.** Because `null` means *bodyweight*, storing a refused value would silently turn a loaded set into a bodyweight one. The History editor therefore keeps an out-of-range weight (and body weight) as the raw typed string, flags the field, and blocks Save via `editInvalid`; the live logger disables Add Set with a message. Clearing a field still means null — that distinction is the whole point.

**Numbers are validated at the input edge, in one place.** `fromInputWeight` / `fromInputReps` / `fromInputBodyWeight` are the only gates between the keyboard and the database, and they reject blank, negative, non-finite and out-of-range values (`MAX_WEIGHT_KG`, `MAX_REPS`). The ceiling is not cosmetic — both weight columns are Postgres `real`, so a value past it fails to insert forever with no retry. **A rejected weight returns `null`, which means bodyweight** — so a caller must refuse it visibly rather than storing it: `ExerciseCard` disables Add Set and shows why, and the quick body-weight log does the same. The import sanitiser (`cleanWeight`, `cleanImportedSet`) applies the identical bounds, so no path is stricter than another.

**Workout identity is the row `id` (uuid).** `deleteWorkout(id)` and `updateWorkout(id, ...)` key by uuid — the Supabase row id, back-filled with `crypto.randomUUID()` for cache entries that predate ids and for optimistic temp rows before the insert returns. `HistoryScreen` resolves `workouts[originalIndex].id` after sorting/filtering and passes the id back, so a reordered subset still routes to the right row. (Exercise identity, by contrast, is still the *name string* — see the "Never rename" convention below; that's the model weakness Phase 1 of [PRODUCT-ROADMAP.md](PRODUCT-ROADMAP.md) addresses.)

## Conventions

- **Exercise catalogue**: `EXERCISES` maps each workout type (`push` / `pull` / `legs`) to an ordered list of `{ group, items }` — the groups are muscle groups, and they're the picker's structure. `CORE` and `CARDIO` are shared: they're appended to all three days, since neither belongs to one. `ALL_GROUPS` (used by `custom`) strips the shared groups out and re-appends them last, rather than deduping in place — dedupe-in-place would leave them at push's position, mid-list. Exercise names must stay unique across all groups: `ALL_GROUPS` flattens them and they're used as React keys.
- **Renaming an exercise is now safe if you pin its id.** Identity is the stable `exerciseId` (slug of the *original* name), not the display string — stamped into stored workouts and used to key `ProgressScreen`'s dropdown/series and the muscle grouping (`groupForExercise`). To rename: change the name in the catalogue **and** add an `EXERCISE_ID_OVERRIDES` entry pinning the new name to the *original* slug (e.g. `{ 'Side Lateral Raise': 'lateral-raises' }`), so old and new sessions share one identity. Renaming the string *without* pinning still orphans history — the override is the supported path. Removing an exercise still orphans its history (nothing maps the id). Adding is always free. `node tests/exercise-identity.test.mjs` guards against a new name slug-colliding with an existing one. **Moving** a name between groups is always safe (identity is the name slug, not the group) — groups only drive the picker's structure and the muscle stats.
- **The muscle taxonomy is a second, parallel map.** `GROUP_TO_MUSCLE` gives each picker group a default muscle and `MUSCLE_OVERRIDES_BY_NAME` lists every exercise whose prime mover differs — that's what the stats donut reads, never the picker group. A missing override fails **silently** (the exercise just scores as its group default), so when adding an exercise check whether it needs one; the identity test asserts every override key is a real catalogue name. Known limitation: `Tibialis Raise` maps to Calves because there's no shin slice in the muscle set.
- The picker's one input does triple duty: it matches a **muscle group** (typing "chest" opens the whole Chest group), otherwise filters **exercise names**, and the **+** button commits whatever was typed as a one-off. Groups with no match drop out rather than leaving a bare heading.
- **Training splits.** `SPLITS` is the list of splits the home card offers — PPL, Upper/Lower, Full Body, Bro, Arnold — each `{ id, label, sub, days }`. `prefs.split` holds the chosen id (`''` = not chosen, which makes the "Start a session" card render the chooser instead of tiles; an account that already has workouts is inferred as `ppl` so returning users are never stopped by it). A day's `name` **is** the stored `workout.type`, so ids must be stable and shared where the day is the same (`legs` is one id across PPL/Bro/Arnold). `CUSTOM_DAY` is appended to every split by `daysOfSplit(id)`. Only PPL's days carry photos; the rest render the photoless tile variant. Adding a split means adding a `SPLITS` entry **and** an `EXERCISES` entry per new day type — composed from the existing groups via `groupsOf`/`dayFrom`, never re-declared (names must stay unique).
- **Sessions start pre-filled.** `STARTER_TEMPLATES` maps each day type to its opening exercise list, and `confirmBodyWeight` seeds the session with `starterExercises(type)` so the user only types reps and weight. Untouched cards cost nothing — `finishWorkout` already drops zero-set exercises, and Finish stays gated on `totalSets === 0`. Template names must match the catalogue exactly (a typo logs a one-off with its own id and orphans the history); `tests/exercise-identity.test.mjs` checks every one. `custom` is deliberately empty. Each `ExerciseCard` also shows a `Last 80 × 8 · …` reference line, fed by the `lastByExercise` map (keyed by `exerciseIdOf`, newest session wins).
- **Days can be renamed.** `prefs.dayNames` maps type id → the user's own label, edited inline on the home card ("Rename days"). It's display-only: the stored `workout.type` never changes, so history, stats, the type filter and the import whitelist all stay keyed off the id. **Read labels through `labelForType(type, dayNames)`, never `TYPE_CONFIG[type].label` directly** — that resolver is what makes a rename show up on the tile, the weigh-in header, the session header, History cards, the filter dropdown and History search at once. `safeDayNames` sanitises the blob on all three load paths (cache, server hydrate, backup import), the same way `hidden` is.
- **`TYPE_CONFIG`** maps workout type → `{ label }` and is the single place that decides how a type is labeled — it's now *derived* from `SPLITS` (first declaration of a shared day wins), so name a day in `SPLITS`, not here. It holds every day type of every split, not just the current one: it labels history forever and it's the import sanitiser's whitelist (a type missing from it folds imported sessions to `custom`). Lookups fall back to `TYPE_CONFIG.custom`.
- **A resumed session keeps its sets, always.** A persisted workout older than `MAX_RESUME_MS` is still restored — only its timer is switched off (`workoutTimer: false`), so `finishWorkout` logs no duration. Throwing the sets away to avoid a silly clock reading trades the user's actual work for a cosmetic fix.
- **Session exercise cards carry a client-only `_uid`.** `newExerciseCard` stamps it; `finishWorkout` strips it before saving, so it never reaches the `exercises` JSONB or an export. It exists because `ExerciseCard` holds the un-committed reps/weight draft in local state — with index keys React bound that draft to a *position*, so reordering a card logged the typed set against the wrong lift.
- **Row-scoped UI state uses the row uuid, never an array index.** `HistoryScreen`'s expand/edit/delete keys are uuids: the `workouts` array is re-sorted, filtered and replaced by hydrate underneath the screen, so a stored index can come to name a different row and Save would hit the wrong session.
- **The rest timer is deadline-based, not decrement-based.** It stores the target time and derives the remainder, because a `setInterval` that ticks `r - 1` only advances while the tab is awake — and a rest timer's whole job is to run while the phone is in your pocket. `visibilitychange` re-derives on return so a rest that expired while hidden completes immediately.
- **Date gaps are counted with `daysBetween`, not `/ 86400000`.** Two local midnights two calendar days apart are 49h apart across a DST fall-back, which read as *more* than the two-day streak tolerance and broke a live streak once a year.
- Charts are recharts (`LineChart`), icons are lucide-react. Both are already imported at the top.
- Mobile-first: layouts are `max-w-*` centered with `sm:` breakpoints, and `.pb-safe` in [src/index.css](src/index.css) handles the iOS home indicator.

## Design system

**Never write a raw colour.** The palette is CSS custom properties in [src/index.css](src/index.css), exposed to Tailwind as semantic colour names in [tailwind.config.js](tailwind.config.js): `ground`, `surface`, `raised`, `line`, `ink`, `muted`, `faint`, `accent`, `accent-ink`, and the semantic `good` / `warn` / `crit`. Use `bg-surface`, `text-muted`, `border-line` — never `bg-zinc-900`. To retheme, edit the tokens, not the components.

Palette source is calibrated Olympic plates: the accent is the 20kg blue, and `good` / `warn` / `crit` are the 10kg green, 15kg yellow, and 25kg red. Neutrals are graphite with a cyan-blue bias taken from bar steel. Keep new colours inside that system rather than introducing a hue from elsewhere.

**Themes are token-level.** `:root` holds light, `@media (prefers-color-scheme: dark)` redefines the tokens, and `:root[data-theme='light'|'dark']` overrides both directions for the in-app toggle. Style through tokens only; never put component rules inside the media query. All four blocks must define the same token set — add a token to one, add it to all four. [index.html](index.html) stamps the saved theme before first paint to avoid a flash.

**Shared class strings** at the top of the app file: `card`, `input`, `btnPrimary`, `btnSecondary`, `btnDanger`, plus `label` (uppercase caption) and `readout` (a number meant to be read at arm's length). Prefer these over ad-hoc classes.

**Type**: Barlow (UI) + Barlow Condensed (`font-display` — numerals, headings, labels), self-hosted via `@fontsource` so the app works offline. Weights are imported individually in [src/main.tsx](src/main.tsx) — importing a weight that isn't there silently falls back, so add the import when you use a new one. Digits use `tabular-nums`.

**Radii** are semantic and deliberately tight: `rounded-card` (10px), `rounded-ctl` (6px), `rounded-chip` (3px). Don't reach for Tailwind's default `rounded-lg`/`rounded-2xl`.

**Motion is minimal and lives in [src/index.css](src/index.css).** Every animation is a keyframed utility class there — `.animate-fade-rise` (auth/onboarding cards) plus the goal-tile set (`.animate-wave` / `.animate-wave-slow`, `.animate-bubble`, `.animate-glow`, `.animate-tile`). A single global `@media (prefers-reduced-motion: reduce)` rule collapses `animation-duration`/`transition-duration` to `0.01ms` for `*` — so honoring reduced-motion is automatic *only* for CSS animation and transition; a JS-driven or SVG `<animate>` motion escapes it and has to opt out by hand. Add new motion the same way — a token-level utility class — rather than inline transitions.

**The weekly-goal tile is a themed-SVG pattern worth copying.** `prefs.goalCardStyle` picks one of **seven** visualisations of week-goal progress (`liquid`, `bubbles`, `mosaic`, `glow`, `ring`, `plates`, `liquidNumber` — the list is `GOAL_CARD_STYLES`, which is also `sanitizePrefs`'s whitelist and Settings' chooser). `WeekGoalTile` dispatches on `style`, with `liquid` as the fall-through default. Three rules hold across all seven: the `tone` is **always** `text-accent` (progress is never recoloured by how close you are — there's deliberately no met-state green), SVG shapes fill with `currentColor` so the token system supplies the colour and no raw hex appears, and each fill animates up from empty on mount. Adding an eighth style means an entry in `GOAL_CARD_STYLES`, a branch in `WeekGoalTile`, and any keyframes as a utility class in `index.css` — not an inline style.

**Recharts takes colour strings, not classes**, so the tokens are mirrored in the `CHART` object as hex per theme. It's the one place hex is allowed — if you change a token's value, update `CHART` to match, or the charts drift from the UI. Chart-bearing components need the resolved `theme` passed down.

**Editing Tailwind config requires a dev-server restart.** Vite caches it; `@apply` of a new token will 500 with "class does not exist" until you restart, even though `npm run build` (a fresh process) succeeds. Don't chase that error in the source.
